# Как разобраться и выложить проект

Это учебный SQL-проект про кухню вымышленного ресторана. Он не использует данные твоего работодателя. Основной материал на английском, чтобы его можно было показать в LinkedIn и на собеседовании.

## Первый запуск

1. Распакуй архив целиком.
2. Открой kitchen.db в программе с поддержкой SQLite.
3. Найди вкладку SQL / Execute SQL.
4. Открой sql/01_analysis_overview.sql и выполни запрос.
5. Сравни результат с results/01_overview.csv.
6. Пройди запросы 03 (меню), 06 (списания) и 08 (блюда выше порога).

Не выполняй 01_schema.sql поверх готовой базы: таблицы там уже созданы. Он нужен, чтобы видеть структуру. Для восстановления готового набора есть scripts/build_database.py: запускать из папки проекта командой python scripts/build_database.py. Он пересоздаёт базу и исходные результаты. После правки SQL запускай python scripts/run_analysis.py: этот файл исполняет именно сохранённые SQL-запросы. Если меняешь расчёты или данные, обнови выводы и картинку перед публикацией — они не обновляются этим скриптом автоматически.

## Что здесь важно понять

- COUNT(DISTINCT order_id) считает заказы. COUNT(*) в таблице позиций считает строки заказа.
- SUM(quantity) считает порции. В одной строке заказа может быть две порции.
- Выручка = количество × цена − скидка по строке. Скидка уже относится ко всей строке.
- Себестоимость порции = сумма количества каждого сырого ингредиента × его цена за кг или литр.
- Food cost = себестоимость / выручка × 100. В проекте это расчётный расход ингредиентов, а не фактический бухгалтерский COGS.
- Contribution = выручка минус ингредиенты. Это не чистая прибыль: зарплата, аренда и прочие расходы здесь не учтены.
- AVG нужно считать на нужном уровне: сначала сумма одного заказа, потом среднее по заказам.
- LEFT JOIN сохраняет даты без списаний. COALESCE заменяет отсутствующие списания на ноль.
- HAVING фильтрует результат группировки. WHERE фильтрует строки до группировки.
- SQL-диалект — SQLite. Некоторые функции дат потребуется изменить при переносе в PostgreSQL или SQL Server.

## Три цифры, которые стоит уметь объяснить

1. Рыбный сэндвич: food cost 43,48%, вклад после ингредиентов 27,46 AED на порцию. Это повод проверить цену и порцию, но не автоматический повод убрать блюдо.
2. Сибас: food cost 34,77%, вклад 63,46 AED на порцию. Процент хуже установленного порога, но абсолютный вклад больше, чем у сэндвича.
3. Креветки и сибас дают больше половины стоимости списаний. По килограммам лидеры другие, поэтому для экономии нужен денежный показатель.

Порог 32% выбран для задачи. Не называй его обязательной нормой для всех ресторанов. Экономия при снижении списаний на 20% — сценарий, а не результат внедрения.

## Перед LinkedIn

Сначала выполни хотя бы четыре основных запроса и измени один из них: например, посчитай только Dinner или поменяй порог HAVING с 32 на 35. Посмотри, что поменялось, и объясни почему. Это полезнее, чем учить текст поста наизусть.

Создай GitHub-репозиторий kitchen-sql-portfolio и загрузи содержимое этой папки, чтобы README.md был в корне. Этот архив сам по себе никуда не опубликован. Затем приложи linkedin_summary.png к посту, возьми черновик docs/LINKEDIN_POST.txt и добавь настоящую ссылку на репозиторий.

Проект можно подать через твой кухонный опыт: тебе знакомы заготовки, порции и списания, а здесь ты учишься смотреть на них через данные. Говори о том, что действительно разобрал. Не выдавай вымышленную базу за данные ресторана и расчётный сценарий за заработанные деньги. Если спрашивают об инструментах или помощи, отвечай честно.

## Чтобы проект стал твоим

- Добавь запрос: топ-5 ингредиентов по списаниям только за август.
- Сравни средний заказ Dinner для Dine-in и Takeaway.
- Объясни, почему нельзя соединить сырые продажи и списания по дате и сразу посчитать SUM.
- Впиши в пост одно наблюдение из своей работы, не раскрывая цифр и документов работодателя.

Для первых запросов не нужен сложный Python: генератор нужен только для воспроизводимости данных. Основная работа здесь — читать SQL и объяснять результаты.
